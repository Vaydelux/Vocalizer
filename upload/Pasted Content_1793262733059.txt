14. BUILT-IN MODEL AND FALLBACK DESIGN

The completed application will eventually ship with a protected, embedded offline separation model.

Prepare for this requirement now.

The built-in model must:

Be bundled in application resources

Include a compatible inference runtime

Be checksum-verified

Be protected against deletion through the Model Manager

Require no internet connection

Be eligible for fallback only when it supports the requested operation

Suggested eventual default: a verified MDX-Net-compatible ONNX vocal/instrumental model, subject to licensing and compatibility verification.

Do not download or embed this model during the initial development phase.

Until it is installed and working, mark the fallback as unavailable.

Fallback decision order:

Validate the user's preferred model.

Check its installed files and adapter compatibility.

Check the requested operation and stems.

Select a supported device backend.

Attempt processing.

On eligible device failures, retry on CPU when supported.

On eligible model failure, select a compatible embedded default.

Clearly notify the user when fallback occurs.

Prevent infinite retry loops.

Report a real error if no compatible model can process the request.

Never silently convert a requested four-stem operation into two-stem output.

Never present a failed separation as successful.
